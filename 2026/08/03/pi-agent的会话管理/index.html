pi-agent的会话管理

本章介绍 pi-agent-core 的会话管理模块——会话的数据模型、存储实现、上下文构建、压缩与分支导航等核心业务，以及背后的关键技术设计。

一、模块介绍

1.1 模块定位

会话（session）是 Agent 与用户之间一段可恢复的对话历史。会话管理模块解决三个问题：

  1. 持久化：把一次对话完整保存下来，进程退出后可以原样恢复；
  2. 上下文构建：从保存的历史中，重新组装下一次发给模型的上下文；
  3. 历史演化：支持在任意历史节点回退、分支、压缩，而不破坏原始记录。

它不是简单的”消息列表”，而是一棵带 parentId 的条目树。所有会话操作都围绕这棵树展开。

1.2 核心抽象

模块由四个层次组成，位于 harness/session/：

抽象 文件 职责
Session session.ts 面向应用的会话门面，提供 append / 读取 / 导航的领域方法
SessionStorage types.ts 存储接口，定义”如何读写一棵会话树”的契约
SessionRepo types.ts 会话仓库，负责 create / open / list / delete / fork 生命周期
SessionError types.ts 统一错误模型，带稳定的错误码

其中 SessionStorage 有两种实现：

  • JsonlSessionStorage：以版本为 3 的 JSONL 文件落盘；
  • InMemorySessionStorage：仅内存，用于测试、临时会话和无需落盘的场景。

SessionRepo 对应两种实现：JsonlSessionRepo 和 InMemorySessionRepo。

三、关键模块设计

3.1 Session：领域门面

Session 类封装对存储的所有领域操作，是应用直接接触的入口。它不关心底层是 JSONL 还是内存，只面向”会话树”这个抽象。

读取侧：

  • getMetadata() / getEntry() / getEntries(cursor) / getLeafId() / getLabel() / getSessionName()；
  • getBranch()：从叶子回溯到根（或压缩边界），返回路径上的条目；
  • buildContext() / buildContextEntries()：构建 LLM 上下文。

写入侧（统一走 appendTypedEntry，自动填 id / parentId / timestamp）：

  • appendMessage() / appendCustomMessageEntry() / appendCustomEntry()；
  • appendThinkingLevelChange() / appendModelChange() / appendActiveToolsChange()；
  • appendCompaction() / appendLabel() / appendSessionName()；
  • moveTo(entryId, summary?)：移动叶子，可选附带分支摘要。

设计要点：Session 自身不产生 id，而是通过 storage.createEntryId() 向存储要 id，这让存储层可以保证 id 在当前会话内唯一。

3.2 SessionStorage：可插拔存储接口

SessionStorage<TMetadata> 定义了一套最小但完整的存储契约：

几个值得注意的约定：

  • append 即持久化：appendEntry / setLeafId 被要求先落盘、再更新内存，保证崩溃时不会丢失已确认的写入；
  • 入口方法全部异步：接口不假设底层是同步文件系统，方便接入远程存储或 SQLite 等后端；
  • 游标分页：getEntries({ afterEntrySeq, limit }) 按追加顺序的序号分页，适合尾部增量读取（如 UI 增量刷新）。

3.3 JsonlSessionStorage：JSONL 文件存储

JSONL（每行一个 JSON 对象）是默认的持久化格式。实现要点：

加载与校验

  • 打开时整文件读取，第一行必须是合法的 session 头部（类型 / 版本 / id / timestamp / cwd 逐字段校验）；
  • 后续每一行解析为一个条目，解析失败会抛出带行号的 invalid_entry 错误；
  • 头部只支持版本 3，旧版本直接报 unsupported session version（不做原地迁移，迁移交给上层或导入流程）。

高效元数据读取

loadJsonlSessionMetadata() 只读文件的前 1 行（readTextLines({ maxLines: 1 })）即可获取会话元数据，用于 Repo.list() 时避免加载整个文件。损坏的会话会被跳过，不影响其他会话被列出。

内部索引

打开后同时维护 byId（id → 条目）、labelsById（targetId → 标签）、currentLeafId，读取无需重新遍历。

3.4 InMemorySessionStorage：内存存储

与 JSONL 实现共享相同的存储契约和标签缓存逻辑，只是不落盘。用于测试、临时会话、无需持久化的场景，也是 SessionStorage 的一个最小参考实现。

3.5 SessionRepo：会话仓库

SessionRepo 管理会话的生命周期（区别于会话内条目的读写）：

JsonlSessionRepo 的实现要点：

  • 会话文件按 cwd 分组存放：<sessionsRoot>/--<encoded-cwd>--/<timestamp>_<id>.jsonl，cwd 中的路径分隔符被替换为 -，避免目录名冲突；
  • list() 只读取每个文件的头部（见 3.3），按创建时间倒序返回；
  • fork() 读取源会话，按 fork 目标截取条目路径，写入新文件，新头部记录 parentSessionPath 指向源。

3.6 SessionError：统一错误模型

所有会话异常都收敛到带错误码的 SessionError：

错误码 含义
not_found 条目或会话不存在
invalid_session 会话文件格式非法（头部缺失 / 版本不支持等）
invalid_entry 某一行条目解析失败
invalid_fork_target fork 目标不是可用的 user 消息或条目
storage 底层文件系统操作失败
unknown 其他未知错误

错误码让上层（TUI、RPC）可以按类型做差异化处理，而不是靠匹配错误文本。

4.1 上下文构建 buildContext

② 的变换管线是可扩展的。SessionContextBuildOptions 提供两个扩展点：

  • entryTransforms：对条目序列的任意变换（在默认压缩变换之后叠加）；

这样读侧成本与历史总长度无关，只与”未压缩部分”相关。

4.3 分支导航与摘要

树结构天然支持分支：moveTo(entryId) 把叶子移动到任意历史节点，之后追加的新条目成为该节点的子节点，形成新分支。旧分支原封不动地保留在树中。

从新分支返回旧分支时，为了不让被放弃的上下文丢失，moveTo() 可附带摘要：

这会追加一条 branch_summary 条目。之后构建上下文时，它会被投影成一段 branchSummary 摘要消息（createBranchSummaryMessage）注入模型，让模型”知道”被放弃分支发生了什么。摘要的生成由上层调用模型完成（见 branch-summarization.ts），会话模块只负责持久化和注入。

4.4 会话 fork

Repo.fork(source, { entryId, position, id }) 从源会话派生一个新会话，用于”从这个点重新开始”：

  • entryId 省略：复制全部条目；
  • position: "at"：叶子落在目标条目上（含该条目）；
  • position: "before"：目标必须是 user 消息，叶子落在它的父节点上（不含该消息），便于编辑后重发。

fork 出的新会话拥有新的 id、新的文件路径和指向源的 parentSessionPath，内容按”叶子到根（或压缩边界）”截取，天然丢弃了旁支。

4.5 标签系统

label 条目为任意条目打用户标签（书签）：

存储层维护 labelsById 缓存，getLabel() 直接返回当前生效的标签。标签是”作用于被标记条目”的特殊条目，因此在 fork 时也需要单独处理，避免产生孤儿子节点。

4.6 会话统计

getSessionStats() 聚合整棵树的用量数据，返回消息数、缓存/非缓存/总 token 以及总成本：

聚合覆盖 message（assistant 的 usage）、compaction 和 branch_summary（各自的 usage），即使历史已被压缩也能统计出完整账单。

五、关键技术

5.1 Append-only：历史不可变

会话采用 append-only 数据模型。任何”回退””分支””压缩”都只追加新条目（leaf、branch_summary、compaction），绝不修改或删除旧条目。这带来三个好处：

  • 崩溃恢复简单：文件只会追加，不会有写坏中间状态；
  • 撤销/回退天然成立：只要叶子指针没丢，任何历史节点都可重新成为当前节点；
  • 审计友好：完整演化过程都保留在树里。

代价是文件会随分支增多而变大，但 tree 结构让”活动分支”的读取成本始终只与当前路径相关。

5.2 双保留机制：retainedTail 与 firstKeptEntryId

压缩后”保留哪些近期消息”有两种记录方式：

机制 保留方式 场景
retainedTail 消息直接内嵌在 compaction 条目上 新格式，读回无需二次查找
firstKeptEntryId 只记录保留起点 id，读回时在树中定位 旧会话 / 迁移期兼容

读回逻辑优先使用 retainedTail（存在即停），否则回退到 firstKeptEntryId。双机制共存保证了与旧数据的兼容，也让新写入更高效。

5.3 版本化头部与严格校验

会话文件带有 version: 3 的版本化头部。解析采用”严格模式”：头部字段逐一校验，任何一条不合法就直接报 invalid_session，而不是静默容忍。严格校验避免了”手改过的坏文件”被当成正常会话，但也意味着模块不做原地迁移——跨版本的兼容由导入流程或上层负责。

5.4 文件系统抽象与 Result 类型

存储和 repo 层不直接依赖 Node 的 fs，而是通过 FileSystem 抽象（返回 Result<T, FileError>，永不抛出）。这让同一套存储实现可以运行在：

  • 浏览器 / Web Worker（远程存储）；
  • 受限的沙箱环境；
  • 未来的 SQLite 等后端。

仓库层用 getFileSystemResultOrThrow() 把 Result 转换为 SessionError，把”底层失败”统一成”会话错误”。

5.5 短 id 生成

条目 id 用 uuidv7().slice(-8) 生成 8 字符短 id，并在当前会话内做碰撞检查。uuidv7 前缀是时间派生的（短时间间隔内几乎不变），因此随机性来自尾部，这正是取末尾 8 位的原因；万一 100 次尝试仍碰撞，则回退到完整 uuidv7。

5.6 与旧版 SessionManager 的设计差异

同仓库的 coding-agent（packages/coding-agent/src/core/session-manager.ts）还有一套同步实现的 SessionManager。两者的核心模型一致（append-only 树、leaf 指针、compaction 感知的上下文构建），主要差异：

维度 旧版 SessionManager 本模块（Session + Storage）
接口风格 同步、单一类 异步、接口分层（Session / Storage / Repo）
leaf 持久化 内存指针，不落盘 显式 leaf 条目
压缩保留 仅 firstKeptEntryId retainedTail + firstKeptEntryId 双机制
状态推导 thinkingLevel / model 另加 activeToolNames
存储后端 内置 JSONL 可插拔，FileSystem 抽象
错误模型 普通 Error SessionError + 错误码

六、全貌串联

用一次完整的会话生命周期串起所有概念：

会话管理模块的价值在于：把”对话”从线性消息列表抽象成一棵可演化、可压缩、可恢复的树，并让持久化后端可插拔。模型的调用、工具的编排、摘要的生成都发生在这棵树的上层，树的读写契约始终保持简单稳定。
