pi的会话压缩机制

本文档介绍 pi-agent-core 的会话压缩（compaction）机制——为什么需要压缩、压缩的三步管线（准备 / 生成摘要 / 持久化）、压缩后上下文如何恢复，以及关键设计取舍。

一、为什么需要压缩

LLM 的上下文窗口有限。对话越长，消息越多，很快就可能超过模型能接受的最大 token 数。压缩的核心思路是：把「距离现在较远的历史」用一段结构化摘要替换掉，只保留「最近的高价值消息」，让模型在有限的窗口内继续工作，同时尽量不丢失任务的上下文。

何时触发压缩

压缩并非在运行时循环中自动触发，而是由外部调用 AgentHarness.compact() 手动发起（见「三、压缩三步管线」）。是否「应该压缩」由阈值判断函数给出：

参数 含义 默认值
contextWindow 模型上下文窗口大小（token） 由 provider 返回
reserveTokens 为摘要 prompt 与模型输出预留的 token 16384
keepRecentTokens 压缩后保留的近期上下文 token 预算 20000

二、核心概念

概念 定义 说明
compaction 一次「压缩历史 + 生成摘要」的完整操作 产出一条持久化的 compaction 条目
summary 结构化摘要文本 按固定格式生成：Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context，外加文件操作元数据
cut point 切割点，保留历史的起点 从末尾向前累计 token，达到 keepRecentTokens 预算时选定
firstKeptEntryId 压缩后保留区第一条消息的条目 id 旧会话（Pi 2.0 迁移期）用它定位保留起点
retainedTail 压缩后保留的近期消息，直接存在 compaction 条目上 新格式；读回时无需在树里二次查找
tokensBefore 压缩前的上下文 token 估算 记录在条目上，供统计与展示
split turn 切割点落在某个 turn 的中间 该 turn 的前半段单独再摘要一次，后半段保留
previousSummary 上一次压缩产生的摘要 用于增量更新（UPDATE prompt），而非从头重写

三、压缩三步管线

一次压缩由三个阶段的函数协作完成，分别对应 compaction.ts 中的三个导出：

3.1 准备阶段 prepareCompaction()

职责：决定「压缩哪些、保留哪些」。它不调用任何 LLM，是纯内存计算。

有效切割点是关键约束：切割点只能落在消息/摘要类条目上，否则保留区起点会带上不完整的消息对。选定后还会向前回溯，跳过前置的非消息条目，保证落在干净的消息边界上。

split turn：若切割点不是 user 消息，说明它落在某个 turn 中间（前一 user 消息在切割点之前）。此时 prepareCompaction() 返回值（CompactionPreparation）中与 split turn 相关的字段为：

字段 含义
isSplitTurn true，标记本次发生了 split turn
turnStartIndex 该 turn 的起点 user 消息索引
messagesToSummarize 切割点之前完整结束的历史
turnPrefixMessages 被切开 turn 的前半段（从 turnStart 到切割点）
retainedTail 被切开 turn 的后半段 + 之后所有消息

split turn 的处理逻辑是「保后缀」：turn 的后半段是正在进行的实际工作，必须保留；前半段（用户请求与早期进展）单独摘要，只为理解保留部分提供背景。

3.2 摘要生成 compact()

职责：把准备阶段选出的历史消息交给 LLM，生成结构化摘要。

摘要调用的独立性

摘要请求是独立于正常对话的请求，刻意与主对话隔离。下表是摘要 LLM 调用（generateSummaryWithUsage）传入的请求选项：

选项 取值 原因
cacheRetention "none" 摘要是一次性请求，写入 prompt cache 无法复用
sessionId 每次调用新的 uuidv7() 隔离路由与缓存，避免污染正常会话
maxTokens min(0.8 * reserveTokens, model.maxTokens) 限制摘要长度，避免摘要本身吃掉全部预留 token
reasoning 仅当模型支持且 thinkingLevel ≠ off 摘要也可利用推理能力

split turn 的前缀摘要（generateTurnPrefixSummary）单独限制输出为 min(0.5 * reserveTokens, model.maxTokens)。

结构化摘要格式

首次压缩使用 SUMMARIZATION_PROMPT，要求 LLM 输出固定结构（## Goal、## Constraints & Preferences、## Progress（Done / In Progress / Blocked）、## Key Decisions、## Next Steps、## Critical Context），并保留精确的文件路径、函数名与错误信息——这些是后续继续工作的关键。

增量更新

若存在 previousSummary（上一次压缩的摘要），改用 UPDATE_SUMMARIZATION_PROMPT：让 LLM 保留旧摘要的全部信息，只合并新消息带来的进展（如把 In Progress 移到 Done、更新 Next Steps）。这样连续压缩不会丢失早期上下文，也不会重复总结同一段历史。

文件操作元数据

extractFileOperations() 从被摘要的 assistant 消息中提取 read / write / edit 工具调用涉及的文件路径，并继承上次 compaction 条目中记录的 details（hook 提供的摘要除外），避免摘要链上文件信息丢失。生成的摘要会追加：

3.3 持久化 appendCompaction()

compact() 只生成摘要数据，不碰存储。写入由 session.appendCompaction() 完成，产出一条 compaction 类型的树条目：

字段 含义
summary 生成的摘要文本
firstKeptEntryId 保留起点条目 id（旧格式定位用）
tokensBefore 压缩前上下文 token 估算
retainedTail 保留的近期消息（新格式）
details 文件操作等实现细节
usage 摘要调用的 provider 用量
fromHook 摘要是否由外部 hook 提供

Hook 协作

Hook 类型 作用
session_before_compact 回调型 可 cancel 取消压缩；或直接返回 compaction 提供自定义摘要（跳过 LLM 调用）
session_compact 通知型 压缩完成后通知观察者，附 compactionEntry 与 fromHook

关键变换有两个：

① 路径截断：getPathToRootOrCompaction 只回溯到「压缩边界」为止，被压缩的历史（compaction 之前的条目）根本不会进入内存，保证读侧成本与历史长度无关。

五、设计取舍

5.1 双保留机制：firstKeptEntryId 与 retainedTail

机制 保留方式 场景
firstKeptEntryId 只记录保留起点 id，读回时在树中定位 旧会话 / Pi 2.0 迁移期兼容
retainedTail 保留消息直接存在 compaction 条目上 新格式，读回无需二次查找

两者并存，读回逻辑优先使用 retainedTail（存在则直接用），否则回退到 firstKeptEntryId 在树中定位。

5.2 增量更新而非重写

连续压缩把上次的 summary 作为 previousSummary 传给下一次生成，用 UPDATE prompt 做增量合并。代价是摘要生成请求会随历史增长而变大，但换来的是早期上下文永不丢失——每次压缩都基于上次摘要，而不是重新读一遍全部历史。

5.3 切割点约束：保完整消息对

切割点只允许落在消息/摘要类条目上，绝不在 toolResult 或配置变更中间切，否则保留区起点会得到孤立的不完整消息。这是保证保留上下文可被模型正确理解的基础。

5.4 摘要请求隔离

摘要调用使用独立 sessionId 与 cacheRetention: "none"，避免污染正常对话的 prompt cache 与路由。代价是每次压缩都付一次完整请求开销，但摘要是一次性操作，收益大于成本。

5.5 手动触发

shouldCompact 提供了压缩时机判断，但运行时循环不会自动调用 compact()——触发权交给上层（调用方在适当时机主动压缩，或由 UI 提供压缩入口）。这避免了压缩打断正常对话流。

六、全貌串联

用一个具体场景串起整条链路：长对话接近上下文窗口上限，用户执行一次压缩，然后继续对话。
