pi-agent的tool call实现

tool_call（工具调用）是 Agent 的必备能力，也是它区别于普通聊天机器人的核心分界。LLM 本身不产生任何外部副作用——它只能输出”工具名 + 参数”这样的调用意图；真正在文件系统、Shell、编辑器上生效的，是工具执行层。

1. 模块定位

tool_call 指”模型决定调用工具”到”工具结果写回上下文”的完整代码路径。模型本身不产生副作用——它只输出调用意图，即 assistant 消息里的一段 toolCall 内容块：

真实副作用（执行命令、读写文件）发生在工具执行层。因此这条路径本质上就是 agent-loop 里的几段顺序代码：找工具 → 校验参数 → 执行 → 生成结果消息。tool_call 模块做的，是在这几段代码中间插入两个可编程拦截点：

  • beforeToolCall：参数校验之后、真实执行之前。可以阻止执行（block）或改写参数；
  • afterToolCall：执行完成之后、结果写回上下文之前。可以按字段修补结果。

拦截点由三个层次的代码协同实现：

  1. packages/agent（定义与执行）：agent-loop.ts 决定”何时调用拦截点、返回后怎么办”，types.ts 定义拦截点的输入输出契约；
  2. packages/agent 的 Agent / AgentHarness（桥接）：自身不实现任何策略，只把拦截点转成 tool_call / tool_result 事件广播给上层；
  3. packages/coding-agent（使用方）：订阅事件并把决定回传给拦截点——例如 permission-gate 扩展检查 bash 命令是否危险，危险则返回 block。

这样分层的直接原因是策略不进核心：核心只保证”执行前一定有机会拦截、执行后一定有机会修补”，至于谁允许、参数要不要改、结果要不要脱敏，全部由上层按需叠加，互不侵入。

2. 关键模块

tool_call 由五个概念模块组成，从内到外是：

  • 执行流水线：唯一真正执行工具的地方。它把一次模型意图变成”找工具 → 参数兼容与校验 → 执行 → 结果消息”四步，并保证每步的失败都变成一条错误结果消息回流给模型。并行/串行执行、截断兜底都属于它的职责。
  • 拦截点契约：流水线两侧的两个固定插口，定义了策略”能做什么、不能做什么”。beforeToolCall 只拿到已校验参数，能阻止执行或改写参数；afterToolCall 只拿到原始执行结果，能按字段修补。流水线只认这个契约，不知道任何具体策略。
  • 策略宿主：持有并注入 hook 的容器。它自身不实现策略，职责是把”代码回调”桥接成”事件广播”（tool_call / tool_result），让策略以订阅者身份挂载，而不是改流水线代码。这也是测试与其他运行时复用同一套拦截语义的通道。
  • 扩展事件层：策略的挂载点。扩展把 handler 注册到事件名上，触发时按注册顺序逐个调用；事件对象共享可变（handler 可原地改写参数），任一 handler 返回 block 即短路。权限、审计、结果脱敏都以 handler 形式存在于这层。
  • 事件类型模型：事件按工具名做强类型区分（内置工具各自携带类型化参数，自定义工具走通用结构），配合类型守卫收窄，让策略代码免于字符串魔数。

当前内置工具

事件类型模型覆盖七个内置工具，其中 read / write / edit / bash 是跨包共用的基础能力（packages/agent 以工厂函数提供，packages/coding-agent 持有完整定义），grep / find / ls 由 coding-agent 自带：

工具 能力 备注
bash 执行 shell 命令 支持超时、中止、流式输出与尾部截断
read 读取文件 支持 offset/limit 分段、默认截断、图片识别
write 写入文件 自动创建父目录，并发变更串行化
edit 精确替换文件内容 基于唯一 oldText，支持模糊匹配与 diff 展示
grep 内容搜索 正则搜索文件内容
find 文件查找 按条件查找路径
ls 目录列举 列出目录条目

除内置工具外，扩展可以通过 registerTool() 注册自定义工具，参数同样走”校验 → 拦截 → 执行 → 修补”流水线；事件模型中对它们以 CustomToolCallEvent（toolName 为任意字符串、input 为通用结构）兜底。

3. 核心类型与接口

3.1 核心层 hook（types.ts）

  • beforeToolCall(context, signal)：输入为 assistant 消息、原始 toolCall 块、已校验的参数和当前 AgentContext；
  • afterToolCall(context, signal)：输入为执行后的原始结果和 isError，输出按字段合并（content / details / usage 为整体替换，无深层合并）。

3.2 扩展层事件（extensions/types.ts）

ToolCallEvent 是按 toolName 区分的判别联合：bash / read / edit / write / grep / find / ls 七个内置工具各自持有强类型 input，其余一律落入 CustomToolCallEvent（toolName: string、input: Record<string, unknown>）。

  • 内置工具可直接用 isToolCallEventType("bash", event) 收窄；
  • 自定义工具需要显式类型参数：isToolCallEventType<"my_tool", MyToolInput>("my_tool", event)；
  • 不能靠 event.toolName === "bash" 直接收窄，因为 CustomToolCallEvent.toolName 是 string，与所有字面量重叠。

4. 关键业务逻辑

4.1 单次工具调用流水线（agent-loop.ts）

校验失败、hook 阻止、hook 抛异常、abort 都会走 “immediate” 分支：不执行工具，直接构造错误结果。工具执行中抛异常同样转为 isError: true 的结果，让模型自行决定是否重试。

4.2 block 语义

beforeToolCall 返回 { block: true, reason } 时：

  • 工具不执行；
  • 循环生成 createErrorToolResult(reason || "Tool execution was blocked")；
  • 该错误结果作为普通 toolResult 消息写回上下文并返回给模型，模型能看到被拒原因并自我修正，而非中断整个循环。

4.3 执行模式

  • 默认 parallel：先顺序完成全部调用的准备与预检（每个调用的 beforeToolCall 都会执行），再并发执行；
  • 全局 toolExecution: "sequential" 或批次中任意一个工具的 executionMode: "sequential" 都会使整批串行（逐个准备 → 执行 → 结束）；
  • 并行模式下完成事件按实际完成顺序发出，但写回上下文的 toolResult 消息仍按 assistant 原始调用顺序排列；
  • 批次终止判定 shouldTerminateToolBatch()：只有每一个最终结果的 terminate === true 时才停止循环。

4.4 截断兜底

stopReason === "length"（输出被 token 上限截断）时，流式参数可能被 JSON 抢救解析出看似合法但不完整的调用。此时 failToolCallsFromTruncatedMessage() 对所有 tool call 一律生成错误结果，要求模型重新发出完整调用，不执行任何疑似残缺的工具。

4.5 错误策略差异（fail-closed vs fail-open）

  • core / harness / coding-agent 的 tool_call 处理：handler 异常向上传播。coding-agent 的 agent-session 会包装成 “Extension failed, blocking execution” 并阻断该工具执行，默认 fail-closed，保证安全敏感的工具不会被静默放行；
  • coding-agent 的 tool_result 处理（emitToolResult）：handler 异常被捕获、经 emitError 上报后继续下一个 handler，默认 fail-open，因为结果修补失败不应破坏主流程。

5. 关键流程

5.1 扩展层事件分发（coding-agent runner.ts:927-948）

emitToolResult（runner.ts:872-925）对称地遍历 tool_result handlers，按字段把修改后的 content / details / isError / usage 合并返回，无修改时返回 undefined。

5.2 接线与 reload（agent-session.ts:468-518）

_installAgentToolHooks() 只在 Agent 实例上安装一次 hook，回调执行时才读取 this._extensionRunner：

  • 扩展 reload 换入新 runner 无需重装 hook；
  • hasHandlers("tool_call") 为 false 时直接返回 undefined，零 handler 时无事件分发开销；
  • 事件中的 input 即核心层校验后的 args，保证扩展看到的是有效参数。

5.3 完整时序（一次工具调用）

5.4 双桥接

Agent（轻量）与 AgentHarness（应用编排）各自把核心 hook 桥接为事件：harness 在 createLoopConfig()（agent-harness.ts:455-484）中直接转发 tool_call / tool_result，携带 toolCallId、toolName、input、content、details、isError、usage，并把返回结果还原为 BeforeToolCallResult / AfterToolCallResult。测试和第三方运行时可以复用同一套拦截语义。
