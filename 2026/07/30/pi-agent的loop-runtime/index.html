pi agent的loop runtime

本文档介绍 pi-agent-core 的运行时循环（runtime loop）框架——整体架构分层、核心概念，以及 AgentHarness / Agent / agent-loop / pi-ai 四层封装的职责与协作。

一、整体架构分层

二、核心概念

概念 定义 说明
turn 一轮「LLM 回答 + 可能的工具调用」的完整回合 一次大模型的调用
run 从用户一次输入到 agent 最终停止的完整执行过程 多轮大模型的调用，一次用户输入的完整响应
session 一次完整的 agent 会话及其持久化存储 包含从会话开始到当前的所有消息历史、配置变更、压缩摘要等数据，以 JSONL 文件存储并支持树形分支结构
phase AgentHarness 当前的操作状态锁，防止并发冲突 避免新 prompt/压缩/导航在已有操作未完成时闯入导致状态错乱。
message 在用户、agent、工具之间传递信息的载体 对话流转和工具结果回传的核心数据单元
steering 用户在一轮run执行过程中，输入的新消息队列 用于实时打断和纠正 agent 方向，当前turn执行完成后会处理该信息
follow-up 用户在 agent 运行时输入、但等到 agent 自然停止前才处理的消息队列 和 steering 相反——这条消息不急着打断当前流程，等 agent 把手头的事都做完（无 toolCall、无 steering）再处理。相当于「先把手头的事收尾，然后再做这个」
save point turn 之间的一致性检查点 agent 运转时修改配置或写入会话不会立即生效，而是排队等到当前 turn 完成后统一刷出。save point 就是「刷出排队变更」的时刻，保证不会在 agent 忙时动状态

三、封装层

AgentHarness 和 Agent 是直接调用 runAgentLoop 的两种封装，分别应对不同场景，使用者按需选其一。

3.1 AgentHarness（编排层）

编排层（AgentHarness）是 Agent 系统的总控制器，承上（coding-agent/UI 调用）启下（Agent 循环），负责管控并发、管理配置、处理事件循环和结算。

管理的五大子系统

子系统 职责
Phase 状态机 互斥锁，保证单轮操作的原子性
配置管理 model/tools/thinkingLevel/resources/streamOptions 的读写
三队列系统 steerQueue / followUpQueue / nextTurnQueue，配合 drain 模式控制消息注入时机
Hook 系统 回调型（8 个，可影响行为）+ 通知型（7 个，只读观察），在外部实现定义
会话管理 整场对话的持久化和恢复——记录消息、配置变更等所有会话数据，支持树形分支结构，确保下次继续对话时上下文不丢失

设计理念

委托而非内聚

AgentHarness 不自已做 LLM 调用和工具执行，而是将所有”做事”的职责委托给下层：

  • LLM 流式调用 → 委托给 pi-ai StreamFn，自带 30+ provider 支持、重试、流式解析
  • turn 循环 + 工具执行 → 委托给 runAgentLoop（agent-loop.ts 的模块级函数），封装了 LLM 调用→工具→下一轮的完整循环

好处：编排层保持薄层，职责单一——只做断言、快照、路由、结算。下层可以独立演化（例如增加 provider 或修改循环策略）而不影响编排逻辑。

配置管理

配置项 内容说明
model 当前 LLM 模型，含 provider / api / baseUrl 等连接信息
thinkingLevel 推理级别：off / low / medium / high
activeToolNames 当前启用的工具名称列表
resources 技能（skills）和提示模板（promptTemplates）资源
streamOptions 传输 / 超时 / 重试 / 认证等 provider 请求设置
systemPrompt 静态字符串或异步工厂函数，每轮 turn 时重新生成

这些配置在 createTurnState() 时快照，运行中的 setter 不影响当前 provider 请求。其中 model / thinkingLevel / activeTools 的变更会写入 session 条目持久化（idle 时立即写，忙时排队）；streamOptions / resources / 队列模式等变更只在内存生效，不持久化。

三队列系统

三者在生命周期中的位置关系：

flowchart TB
    Input["用户输入"] --> Prompt["prompt 入口"]
    NextTurn["nextTurnQueue"] -.->|下次 prompt 注入| Prompt

    Prompt --> Loop{"turn 循环"}

    Loop --> LLM["LLM 调用"]
    LLM --> Tools["工具执行"]
    Tools --> Steer{"steerQueue\n有消息？"}
    Steer -->|有| Loop
    Steer -->|无 且 无工具执行| FollowUp{"followUpQueue\n有消息？"}
    FollowUp -->|有| Loop
    FollowUp -->|无| End["agent_end"]
队列 消息来源 消费时机
steerQueue 用户在当前 run 中输入，想打断 agent 当前思路 每个 turn 完成后、下个 LLM 调用前取出，实现即时干预
followUpQueue 用户在当前 run 中输入，但不急 agent 即将停止时才取出，让 agent 先把手头事收尾
nextTurnQueue 外部调用 public nextTurn() 注入 下个 prompt 时合并到用户消息之前，属于系统级注入

drain 模式控制每次取出多少条：

  • one-at-a-time（默认）：每次只取最早一条，剩下的下次再取
  • all：一次性取出所有消息

Hook 系统

分为两类，注册方式不同：

回调型（handler 可返回结果影响行为）：

Hook 可修改的内容 用途
before_agent_start messages, systemPrompt prompt 前注入消息/覆盖系统提示
context messages 变换消息列表（剪枝/注入上下文）
before_provider_request streamOptions 按请求修改传输/超时/重试选项
before_provider_payload payload 修改 LLM 请求体
tool_call block, reason 拦截工具调用，模型收到错误结果后重试
tool_result content, isError, terminate 修改工具结果（例如隐藏敏感内容）
session_before_compact cancel, compaction 取消压缩或提供自定义摘要
session_before_tree cancel, summary 取消树导航或提供自定义分支摘要

通知型（通过 subscribe(listener) 观察，"*" 通道，只读不可修改行为）：

事件 说明
after_provider_response provider 响应后，可观察 status / headers
session_compact 会话压缩完成
session_tree 树导航完成
model_update model 配置变更
thinking_level_update thinkingLevel 配置变更
resources_update resources 配置变更
tools_update 工具列表或活跃工具变更
queue_update 队列状态变更（steer / followUp / nextTurn）
save_point 保存点（turn 完成 + 持久化后）
abort 中止完成
settled 完全结算
retry_scheduled 压缩 / 分支摘要重试已调度
retry_attempt_start 重试开始
retry_finished 重试结束

会话管理

负责整场对话的持久化和恢复——记录对话中发生的每一件事（消息、模型切换、工具开关等），确保下次继续对话时上下文不丢失。

读侧：每轮 turn 开始前，从磁盘 JSONL 文件中读取历史消息和最新配置，还原成 agent 可理解的上下文。同时识别压缩标记，跳过已被摘要替换的历史，避免上下文过长。

写侧：对话进行中持续记录新产生的内容。但 turn 运行时直接写入文件可能造成冲突，因此将写入请求暂存到缓冲区，在 turn 之间的安全点（save point）统一写入。

写入什么 什么情况下触发 写入到哪里
用户/助手/工具消息 每轮 LLM 调用或工具执行完成后 session 消息条目
模型切换记录 用户切换模型时 session 配置变更条目
推理级别变更记录 用户调整推理级别时 session 配置变更条目
工具开关记录 用户切换工具集/活跃工具时 session 配置变更条目（active_tools_change）

分支能力：会话以树形结构组织，支持从任意节点分叉出独立分支，每次读取时从当前叶子回溯到根。

数据安全保障：异常时 finally 块兜底刷出，保证排队中的写入不会丢失。

3.2 Agent（有状态封装层）

有状态封装层（Agent）是 runAgentLoop 的一个轻量封装，为不需要编排层（AgentHarness）全套基础设施的场景提供独立的入口。它的作用只有三个：

  1. 管并发 — 保证同一时刻只有一个 run 在执行，支持 abort
  2. 存消息 — 维护当前 transcript（messages），事件驱动更新
  3. 收投消息 — 提供 steer/followUp 队列，支持在 run 进行中注入消息

Agent 不决定何时停止、不管理配置、不持久化会话。需要这些能力的场景应直接用 AgentHarness（它跳过 Agent 层，直接调用 runAgentLoop）。

管理的五大内部结构

结构 职责
MutableAgentState 运行时可变状态：messages / tools / systemPrompt / model / thinkingLevel / isStreaming / pendingToolCalls
PendingMessageQueue steering 和 follow-up 消息队列，支持 one-at-a-time / all 两种 drain 模式
ActiveRun 当前执行中的 run 句柄，含 promise / abortController，保证同一时刻只有一个 run 执行
Listener 集合 外部 subscriber 注册的事件处理器，在 processEvents 中被顺序 await
公共回调字段 convertToLlm / transformContext / streamFn / hook 函数（beforeToolCall / afterToolCall 等），由构造时注入或直接公开赋值

设计理念

Bridge 而非 Controller

Agent 不自已驱动循环，而是：

  • 快照状态 → createContextSnapshot() 对 messages/tools 做浅拷贝，传递给无状态循环
  • 装配配置 → createLoopConfig() 将公共回调字段、队列 drain 函数、hook 组装为 AgentLoopConfig
  • 委托执行 → 调用 runAgentLoop() 或 runAgentLoopContinue()，传入 snapshot + config + event handler
  • 归约事件 → processEvents() 将无状态循环发出的 AgentEvent 映射回内部状态变更

好处：无状态循环保持纯函数特性（给定输入 → 输出事件流），Agent 层管理副作用的订阅和状态同步。循环逻辑的修改不影响状态管理 API，反之亦然。

流程全貌

并发模型

机制 说明
activeRun 哨兵 prompt() / continue() 入口检测 this.activeRun，非空则抛 "Agent is already processing"
AbortController 每次 runWithLifecycle 创建新 AbortController，通过 signal 下传。abort() 方法供外部主动取消
waitForIdle 返回 activeRun.promise，在 finishRun() 中 resolve，调用方可 await 当前 run 结束

消息队列

方法 队列 drain 时机（由无状态循环消费）
steer(message) steeringQueue 每个 turn 完成后、下个 LLM 调用前
followUp(message) followUpQueue agent 即将停止时（无 toolCall + 无 steering）
clearSteeringQueue() / clearFollowUpQueue() / clearAllQueues() — 外部主动清空

drain 模式通过 steeringMode / followUpMode 属性在运行时切换，默认均为 one-at-a-time。

外部 API 清单

方法 用途
prompt(input, images?) 启动新一轮对话或追加系统消息
continue() 从当前 transcript 继续（最后一条须为 user 或 toolResult）
steer(message) 插入干预消息，当前 turn 完成后生效
followUp(message) 插入延后消息，agent 即将停止时生效
abort() 中止当前 run
reset() 清空 transcript、队列和运行时状态
subscribe(listener) 注册事件监听器，返回取消函数
waitForIdle() 等待当前 run 及其所有 listener 结束

关键点：Agent 是 runAgentLoop 的轻量封装，维护可变 transcript 和 steer/followUp 队列，提供可中断、可订阅的 API。需要会话持久化、配置管理和 Hook 系统的场景应使用 AgentHarness。
